What this is

A neural network that learns what a healthy bearing sounds like — nothing else — and flags anything it can't reconstruct as a possible fault. No fault examples are shown during training; the only supervision is "this machine was fine while this signal was recorded."

The model is an autoencoder: it compresses each ~0.7-second window of vibration into 128 numbers, then tries to rebuild the original signal from just that compressed code. Trained exclusively on healthy running, it gets very good at rebuilding healthy vibration and measurably worse at rebuilding anything that isn't — a bearing fault, in particular. That reconstruction error, compared against a threshold calibrated purely from healthy data, is the entire detection mechanism.

Built and tested against the CWRU bearing dataset — a public benchmark of lab-recorded accelerometer data from healthy and seeded-fault bearings — as a stand-in for real turbo-pump sensor data, which doesn't exist yet for this project. The dataset's fault labels are never shown to the model; they're used only afterward, to check whether the unsupervised detector actually found the faults.

How it works

1

Windowing

Long raw accelerometer recordings are cut into fixed-length overlapping chunks (~0.7s, ~21 shaft revolutions at the rig's speed) — the unit the rest of the pipeline operates on.

2

Short-Time Fourier Transform

Each window becomes a 128×128 log-magnitude spectrogram — a linear-frequency image, deliberately not a Mel-spectrogram: Mel scaling exists for human pitch perception and would blur exactly the frequency detail that separates bearing fault signatures.

3

Autoencoder, trained healthy-only

A convolutional encoder compresses the spectrogram to 128 numbers (a 128× compression ratio); a mirrored decoder reconstructs it. Every training example — never a fault — comes from three of the four recorded load conditions, so the model never even sees the specific load condition it's later tested on.

4

Reconstruction error

Mean squared error between input and reconstruction. Low for anything resembling the healthy patterns the model trained on; measurably higher for anything that doesn't fit — which is exactly what a fault produces.

5

Threshold and flag

The threshold is the 99th percentile of reconstruction error on held-out healthy validation data — chosen before ever looking at a fault label, simulating a real deployment where fault examples aren't available to tune against.

Does the bottleneck size actually matter the way we claimed?

The design notes for this model reasoned that the compression ratio is the single most important knob: too small and the model can't rebuild even healthy signal well; too large and it starts rebuilding faults too, both hurting separation. That was a prediction, not yet a measurement — so it got tested: eight otherwise-identical models, trained and evaluated with nothing changed except latent_dim, from 4 up to 512.

The prediction didn't hold, and that's itself informative. ROC-AUC stayed at 1.000 and F1 stayed ≥ 0.999 at every single value tested — CWRU's healthy/faulty separation is apparently easy enough that even a 4-number bottleneck (a 4,096× compression of the 128×128 input) captures it fully. The aggregate metrics saturate too fast to show the tradeoff. A more sensitive number — raw false-alarm count on the 57 held-out healthy windows — shows a faint version of the expected pattern underneath that saturation:

How to run this yourself

Everything is driven by one config file (configs/default.yaml) and a handful of CLI stages — download → train → evaluate → infer, plus analyze and sweep for the deeper checks above. Two ways to actually execute it:

On Kaggle used for this report

No local install needed — runs on Kaggle's infrastructure via their API, CPU-only, reading data from an attached public dataset (no internet access required inside the kernel).

# regenerate notebook from source + push
bash scripts/05_kaggle_push.sh
# poll until COMPLETE
bash scripts/06_kaggle_status.sh
# pull logs + figures + trained model
bash scripts/07_kaggle_pull.sh

Locally needs a venv + PyTorch

Once a Python env has requirements.txt installed, every stage is a plain module invocation:

# fast smoke tests, no dataset needed
python -m pytest
# full pipeline
bash scripts/02_train.sh
bash scripts/03_evaluate.sh
bash scripts/04_infer_demo.sh

Data itself: 64 twelve-kilohertz Drive-End accelerometer recordings (healthy + three fault types × four severities × four load conditions), either downloaded fresh from a GitHub mirror of the CWRU dataset or read from a pre-attached Kaggle dataset in the same format. tests/test_smoke.py covers the plumbing — windowing shapes, spectrogram shapes, model forward pass — against synthetic data, no download required.

Limitations

Read this before trusting the headline numbers
  • CWRU is a well-known "easy" benchmark. Clean lab recording, no cross-talk from nearby equipment, no piping-induced vibration, none of the sensor noise a real industrial deployment has. The near-perfect separation above reflects that as much as it reflects the method.
  • Faults are instantaneous and machined, not developed. Electro-discharge-machined defects at a fixed severity — not the gradual wear a real predictive-maintenance system needs to catch trending toward failure.
  • The test set's class balance is artificial. Built to include every fault file for evaluation power, not to mimic how rarely a real healthy-running pump would actually fault.
  • Bearing data, not pump data. No turbo pump dataset exists for this project yet — CWRU is a stand-in chosen because it's a real, labeled, widely-used rolling-element-bearing benchmark, not because it resembles a turbo pump's full failure mode set.
  • Single sensor, single axis. One accelerometer, one measurement direction — no sensor fusion.

None of this makes the result above meaningless — it's real evidence that the architecture, training procedure, and evaluation methodology work correctly end to end on real data. It's evidence the pipeline works, not a guarantee about what it would find on an actual pump.
