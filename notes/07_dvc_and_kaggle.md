# DVC and Kaggle

## DVC (data version control)

**Why**: `data/raw/` (187MB, 65 files) is exactly the kind of thing git
handles badly — large binary files with no meaningful diff. DVC tracks it
as a single content-addressed hash instead, so git only ever stores a tiny
pointer file, while the actual data is cached/versioned separately.

**What's set up**: `dvc init` created `.dvc/config`, `.dvc/.gitignore`, and
`.dvcignore` (all git-tracked — DVC staged them itself). `dvc add data/raw`
then:
- moved `data/raw/`'s content into DVC's local cache (`.dvc/cache`,
  content-addressed by MD5),
- wrote `data/raw.dvc` — a small, git-tracked pointer file (dir hash + file
  count + size),
- generated `data/.gitignore` with `/raw` in it, so git no longer tracks
  the actual files directly (DVC does).

`data/raw/` still looks and works exactly the same on disk (all 64 `.npz` +
`MANIFEST.txt` are still right there) — the only change is *how git treats
it*. `data/processed/` (the regenerable spectrogram cache) is deliberately
**not** DVC-tracked — it's cheap to regenerate from `data/raw/` + code (see
`data/README.md`), so versioning it would just be noise.

**The gap**: no DVC **remote** is configured yet. That means `dvc push` /
`dvc pull` have nowhere to go — the data is versioned locally (reproducible
on this machine, and `git clone` + `dvc checkout` would work if you cloned
this repo onto another local path), but not yet shareable to another
machine or backed up off this one. To fix that, pick a remote and run:

```bash
# example: an S3 bucket
.venv/bin/dvc remote add -d storage s3://your-bucket/vibration-ad
# example: a local external drive or network share (no cloud account needed)
.venv/bin/dvc remote add -d storage /Volumes/SomeExternalDrive/dvc-storage
# then:
.venv/bin/dvc push
```

Left for you to decide since it depends on what storage you actually have
access to — didn't want to invent a fake remote you'd have to unwind later.

**Day-to-day workflow** once this matters (e.g. after retraining produces a
new model checkpoint you want versioned):
```bash
.venv/bin/dvc add outputs/models        # if you decide to track trained models too
git add outputs/models.dvc outputs/.gitignore
git commit -m "..."                     # you do this yourself, per your workflow
.venv/bin/dvc push                      # once a remote is configured
```

**Aside — why pip, not brew**: `brew install dvc` was attempted first and
aborted: on this machine's Homebrew setup it triggered building rustc, gcc,
boost, aws-sdk-cpp, and grpc *from source* (no prebuilt bottles available
for this OS/arch combination for one of dvc's transitive dependencies) —
that's an hours-long compile chain for a CLI tool, so it was killed and the
partial download cache cleaned up. `pip install dvc` into the project's own
`.venv` used prebuilt wheels instead — done in about 2.5 minutes, no
compilation. `dvc` now lives at `.venv/bin/dvc` (same "always call the venv
binary directly" pattern as everything else in this project — see
`notes/00_project_overview.md`).

## Kaggle: testing the PyTorch pipeline without a local install

**Why**: your local `.venv` exists but is intentionally empty for now (you
said installing `requirements.txt` — mainly PyTorch — can wait). Kaggle
Notebooks give free GPU compute with PyTorch already installed, so it's a
way to actually exercise the model/train/evaluate code for real before
committing to a local install.

**What's set up**: `notebooks/kaggle_train.ipynb`, generated by
`scripts/build_kaggle_notebook.py` (stdlib-only, run with any Python 3;
re-run it and re-push if the source changes — it's a snapshot, not synced),
plus `notebooks/kernel-metadata.json` (git-tracked, describes the kernel to
the Kaggle API: id, title, GPU/internet flags, private). The notebook:

1. Reconstructs the entire `vibration_ad` package + `configs/default.yaml`
   + `data/raw/MANIFEST.txt` on disk from base64-embedded copies of the
   real files (read directly off disk when the generator runs — no
   hand-transcription, verified byte-identical to the repo before this was
   written down as done).
2. Confirms PyTorch + GPU are available (`torch.cuda.is_available()`).
3. Downloads the same 64 CWRU files from GitHub (needs the notebook's
   *Internet* setting ON).
4. Runs `train.py` → `evaluate.py` → `infer.py` exactly as `scripts/*.sh`
   would locally, then displays the generated plots inline.

**How it actually runs — the Kaggle API, not manual upload.** Turns out
`~/.kaggle/access_token` already existed on this machine (username
`AghZuzu`, from some earlier Kaggle CLI use) — so no credential exchange
was needed, and everything below runs through the API rather than the
browser:

```bash
.venv/bin/python -m pip install kaggle   # already done, wheels, ~10s
.venv/bin/kaggle kernels init -p notebooks   # scaffolds kernel-metadata.json (one-time)
# kernel-metadata.json (git-tracked) points code_file at kaggle_train.ipynb,
# sets kernel_type=notebook, enable_gpu=true, enable_internet=true, is_private=true
.venv/bin/kaggle kernels push -p notebooks   # regenerates + pushes a new version
.venv/bin/kaggle kernels status aghzuzu/vibration-anomaly-detection-mvp
.venv/bin/kaggle kernels output aghzuzu/vibration-anomaly-detection-mvp -p outputs/kaggle_run
```
Wrapped as `scripts/05_kaggle_push.sh` / `06_kaggle_status.sh` /
`07_kaggle_pull.sh`. The kernel runs on Kaggle's infrastructure
asynchronously (push returns immediately) — poll status until it's
`KernelWorkerStatus.COMPLETE` (or `.ERROR`), then pull. Live view:
https://www.kaggle.com/code/aghzuzu/vibration-anomaly-detection-mvp
(there's also a pre-existing unrelated kernel on this account,
`bearing-failure-runner` from 2026-08-12 — left untouched, different slug).

**Two real bugs found and fixed by actually running this** (version 1 of
the kernel failed on both):

1. `!python -m vibration_ad.train ...`-style shell-magic calls don't see
   the `sys.path.insert()` done earlier in the same notebook — that only
   affects the current Python process, not subprocesses spawned by `!`. On
   top of that, bare `python` on Kaggle's `!` shell resolved to
   `/usr/bin/python3`, a *different*, bare interpreter than the notebook
   kernel's own (which has torch/numpy/etc). Fixed by switching every call
   to `subprocess.run([sys.executable, ...], check=True)` and setting
   `os.environ['PYTHONPATH']` (subprocesses inherit env vars, not
   `sys.path`) — see the `run()` helper in
   `scripts/build_kaggle_notebook.py`. `check=True` was also a deliberate
   choice: `!` shell failures print an error but let the notebook keep
   going to the next cell, which is exactly what let this hide until a much
   later cell crashed on a missing output file instead of failing where the
   real problem was.
2. Despite `enable_gpu: true`, the first run logged `torch: 2.10.0+cpu` and
   `cuda available: False` — GPU wasn't actually granted for that session.

**A third issue, version 2 (not a code bug, needs action on kaggle.com)**:
version 2 (with bug #1 fixed) ran for 35 minutes and then failed inside
`train.py`'s dataset build with "No .npz files found." The actual cause,
from the kernel log: every single download attempt failed with
`<urlopen error [Errno -3] Temporary failure in name resolution>` — i.e.
DNS didn't resolve, no internet access at all in that session, despite
`enable_internet: true`. Combined with bug #2 (no GPU despite
`enable_gpu: true`), this points at one root cause rather than two: **Kaggle
gates both internet access and GPU/TPU in kernels behind phone number
verification on the account** — an unverified account gets both silently
disabled no matter what the kernel-metadata.json / notebook sidebar says.
Fix (if you want internet + GPU to actually work): kaggle.com → account
settings → verify a phone number. Not something doable from the API/CLI.

Separately, `download.py` had a real robustness bug this exposed: it caught
per-file failures and logged them but never raised, so a *total* download
failure (0/64 files) still let the pipeline continue past that stage as if
nothing were wrong — the failure only surfaced 35 minutes later, in a
different module, with a confusing message. Also: each failed attempt was
taking ~30s (the OS default DNS resolver timeout, since no explicit
timeout was set), which is most of why 64 failures ate 35 minutes. Fixed
in `download.py`: explicit 15s request timeout, abort after 3 consecutive
failures instead of grinding through the whole manifest, and raise
`RuntimeError` if anything failed so the notebook's `check=True` catches it
immediately. Verified locally (both the normal skip-existing path and a
simulated total-DNS-failure path) before re-pushing as version 3.

If you'd rather not use the CLI/API for some future run, the manual path
still works exactly the same way: kaggle.com → Create → New Notebook →
File → Import Notebook → upload `notebooks/kaggle_train.ipynb` → set
Accelerator + Internet in the sidebar → Run All -- though per the above,
that sidebar toggle won't actually grant internet/GPU on an unverified
account either.

**A workaround attempted and abandoned: uploading the data as a Kaggle
input dataset instead.** Since GPU wasn't needed (CPU is fine -- matches
this machine, which also has no GPU), the internet block was the one
actually stopping progress, because *something* still has to get the CWRU
data into the kernel. Kaggle input datasets are readable from
`/kaggle/input/` even in a kernel with no internet access -- that's the
whole point of the feature, competitions run this way all the time -- so
the plan was: upload data/raw/ once as a private dataset from this machine
(which has internet), attach it to the kernel, skip the runtime download
entirely. Set up `kaggle_dataset/dataset-metadata.json` and
`scripts/08_kaggle_dataset_push.sh` for this.

It doesn't work, for a reason unrelated to Kaggle: every upload attempt
failed with a Google Cloud Storage `403 "We're sorry, but this service is
not available in your location"` -- reproduced down to a 24-byte text
file, so it's not about the data itself. Diagnosed by temporarily patching
the installed `kaggle` package to print the raw HTTP response (the CLI
swallows it, just prints "Upload unsuccessful"). Checking this machine's
apparent public IP put it in Tajikistan, and there are several VPN client
configs installed (V2Box, Betternet, Speedify, Star VPN) though none show
as actively connected via macOS's standard VPN profile list -- something
is routing this machine's traffic non-locally, and Google's upload
endpoint for Kaggle's dataset storage is geo-blocking it. This is a
property of *this machine's* network path, separate from the
Kaggle-account phone-verification issue -- fixing one doesn't fix the
other. `kernel-metadata.json` and `kaggle_train.ipynb` were reverted back
to the plain GitHub-download approach as a result (simpler, and once phone
verification is done, it just works -- no need to also untangle the
network/VPN situation for dataset uploads). `08_kaggle_dataset_push.sh` is
left in place, clearly marked blocked, in case the network situation
changes and it's worth revisiting.

**RESOLVED: attach an existing public Kaggle dataset instead of downloading
or uploading anything.** You pointed out Kaggle already hosts CWRU data, so
there was no need to get our own copy in there at all. This is strictly
better than both earlier approaches: unlike the GitHub download, attached
input datasets are readable from `/kaggle/input/` with no internet access
needed (sidesteps the phone-verification block completely, not just the
GPU half of it); unlike our own upload, it's *already on Kaggle's
storage*, so nothing has to leave this machine (sidesteps the Google Cloud
Storage geo-block too).

Your two candidate links (`sufian79/cwru-mat-full-dataset`,
`astrollama/cwru-...`) are both raw `.mat`, confirmed via
`kaggle datasets files <ref>` (no need to guess from the JS-rendered
webpage). Went looking more broadly (`kaggle datasets list -s CWRU`) and
found `esraakhaled299/cwru-data`, which turned out to be an excellent
match: pre-organized as `CWRU_organized/12k_DE/Load_{0-3}/{Ball,
InnerRace,OuterRace}/<code>_<load>.mat` plus `CWRU_organized/Normal/
Load_{0-3}/Normal_<load>.mat` — same 64 files, same fault-type/severity
breakdown as our own `data/raw/MANIFEST.txt`, just `.mat` instead of
`.npz` and organized into folders instead of RPM-prefixed filenames.

Two things had to be discovered empirically rather than assumed (both via
a disposable diagnostic kernel, `notebooks/inspect_kernel/` — cheap to
push/check since it does nothing but inspect and exits in ~20s):
1. **Mount path is `/kaggle/input/datasets/<owner>/<slug>/...`**, not the
   commonly-documented `/kaggle/input/<slug>/...` — confirmed by listing
   `/kaggle/input` rather than guessing (a real run had already failed once
   from a wrong hardcoded guess). The conversion cell now searches for the
   dataset's known top folder name under `/kaggle/input` instead of
   hardcoding a path, so it doesn't matter if this changes again.
2. **`.mat` internal key format**: exactly as CWRU's own docs describe --
   `X<id>_DE_time` / `X<id>_FE_time` / `X<id>_BA_time` / `X<id>RPM`, where
   `<id>` is an arbitrary numeric ID that varies per file (not derivable
   from the filename). The conversion code matches by suffix (`.endswith
   ('_DE_time')`) rather than hardcoding an ID.

The conversion cell (in `kaggle_train.ipynb`, generated by
`scripts/build_kaggle_notebook.py`) parses the folder/file structure into
our exact `{rpm}_{fault}_{size}_DE12.npz` / `{rpm}_Normal.npz` naming
convention and saves with the `DE` key our `catalog.py`/`dataset.py`
already expect -- **zero changes to the core package**, only the Kaggle
notebook's data-acquisition step differs from the local pipeline (which
still downloads from GitHub, unaffected by any of this).
